# テストコード作成規約

テストの追加・変更時に使う。対象・期待値は[AGENTS.md](../../AGENTS.md)に従って合意する。既存テストは変更時に合わせる。

## 1. 冒頭に関数ごとの検証内容を書く

`import`より前に、全テスト関数を定義順で列挙する。

```swift
// テスト一覧:
// - saveFailurePreservesDraft(): 保存失敗時のエラー表示と編集内容の保持を検証する。
// - staleResponseIsDiscarded(): 再接続後に古い応答を破棄することを検証する。
```

引数付きも`関数名()`と略記し、入力パターンを説明に含める。同名関数は`Suite名.関数名()`で区別する。補助関数は含めず、テスト変更時に一覧も更新する。

[要求仕様](requirements.md)に対応するテストは、検証内容の前に`[TAB-F-001]`のように要求IDを書く。

## 2. 実装の責務に合わせて置く

| 対象 | 配置・役割 |
| --- | --- |
| GUI | `whubTests/Features/<Feature>/Store・View・Model/`。実装に対応するディレクトリへ分ける |
| Package | `Packages/WhubPackage/Tests/<Target名>Tests/` |
| 共通部品 | `whubTests/Components/`。部品の振る舞いを検証する |
| 共有補助コード | `whubTests/Helpers/`。一つのファイル専用なら、その中で`private`にする |

Storeは状態遷移・保存・エラー、Viewは表示・入力・フォーカスを検証する。結合テストは代表的な操作に絞る。空ディレクトリや、単純な色・余白だけのテストは増やさない。

## 3. 一つの振る舞いを検証する

1. ファイル名・Suite名を`<対象名>Tests`で揃え、`@Suite struct`を使う。
2. 関数名は英語のlowerCamelCaseで条件と期待結果を表す。必要なら`@Test("日本語の説明")`を付ける。
3. 本文は「準備・操作・検証」を空行で区切る。同じ振る舞いに必要な検証は複数あってよい。
4. 結果は`#expect`、後続に必要な前提は`try #require`で確認する。エラーは`#expect(throws:)`で型を絞り、必要な値も確認する。空の`catch`や`try?`で失敗を隠さない。
5. 入力だけ違うケースは`@Test(arguments:)`でまとめる。複数配列は全組み合わせになるため、対にした入力にはタプル配列や`zip`を使う。

## 4. 状態を分離し、条件を待つ

- テストごとにデータ・DB・接続等を用意し、`defer`等で後片付けする。実行順・実データ・稼働中のサービスに依存させない。
- 非同期処理は固定時間のsleepだけで判断せず、応答や状態を待つ。待機には期限を設け、超えたら失敗させる。Taskも終了させる。
- 既定の並列実行を前提にする。`@MainActor`は非同期テスト全体の排他を保証せず、`.serialized`も別Suiteとの競合を防がない。

## 5. 実行した範囲を記録する

変更した振る舞いのテストと、影響する呼び出し側を確認する。[ビルド手順](../operations/build.md)に従い、コマンド・成否・未確認事項をIssueへ記録する。ビルド成功とテスト成功、画面確認を区別する。期待値の変更には仕様変更の理由と合意を残す。

TDDの適用やCIの導入は別途判断する。Swift Testingの機能は[公式資料](https://developer.apple.com/documentation/testing)を参照する。
