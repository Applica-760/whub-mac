# 要求仕様の書き方

機能ごとの要求を`docs/specifications/<機能名>.md`に書き、合意後に[テストコード](testing.md)へ落とす。この文書は、その書き方の規約。

## 1. 要求に固定IDを付ける

- IDは`TAB-F-001`のように機能名・分類・連番で付ける。分類はF（機能要件）、N（非機能要件）、D（設計上の保証）とし、機能名・分類ごとに連番を振る。改名・並べ替えでも変更せず、削除したIDは再利用しない。
- 1つの要求には、合否を判定できる1つの振る舞いを書く。Featureで期待結果が異なる場合は分ける。
- 利用者から見える結果を書く。クラス名・関数名・内部の実装方法は、必要な制約がある場合だけ書く。
- 合意した要求を文書に載せる。未決事項と合意までの議論は作業Issueに残す。

## 2. 前提・操作・期待結果で書く

```md
## TAB-F-001：FileEditorの最後のタブを閉じる
- 前提：未保存の変更がないFileEditorタブが1枚ある
- 操作：CmdWを押す
- 期待結果：そのタブが閉じ、タブが0枚になる
- 対応テスト：未作成
```

「対応テスト」には`ファイルパス / Suite名.関数名()`を記載する。1つの要求に複数テストを対応させてもよい。上のIDは書式例であり、個別仕様の登録ではない。

## 3. テスト側にも要求IDを書く

[testing.md](testing.md)の冒頭一覧にIDを添える。

```swift
// テスト一覧:
// - closingLastEditorTabLeavesNoTabs(): [TAB-F-001] 最後のFileEditorタブを閉じると0枚になることを検証する。
```

要求の一部だけを検証するテストには、何を確認するかを書く。技術的な補助テストすべてに、無理に要求IDを割り当てない。

## 4. 変更と検証を追えるようにする

要求を変更するときは、理由をIssueに記録し、対応するテストと冒頭コメントも見直す。新しい振る舞いへ置き換える場合は旧IDを廃止して新規IDを付ける。削除・廃止した要求の履歴はGitで追う。

テストとの対応付けと、検証成功は区別する。実行結果はコマンド・対象コミット・成否・未確認事項とともにIssueへ記録する。テスト成功だけで、その要求全体を検証済みと扱わない。

参考：[要求IDと検証の対応表（NASA）](https://www.nasa.gov/reference/appendix-d-requirements-verification-matrix/)、[前提・操作・期待結果の記法（Cucumber）](https://cucumber.io/docs/gherkin/reference/)。このMarkdownの形式とIDの運用はWhubの規約。
